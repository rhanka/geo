## 2. D06 — validation détaillée (immo D03 ↔ contrat servi geo)

**2.1 La clé de jointure — déjà servie, à l'identique.** SPEC_GEO_SERVED_CONTRACT §2 : la clé geo
généralisée est **`{ city_slug, zone_ref_canon_v1, reglement_number }`** — mot pour mot celle nommée par
D06. `zone_ref_verbatim = feature.properties.zone_code`, `zone_ref_canon_v1 =
canonicalizeZoneCodeForJoin(zone_code)`, `reglement_number = feature.properties.reglement_numero`.
Le manifeste fige le chemin + SHA de l'implémentation de canonisation. **→ D06 n'a pas à inventer une clé :
geo la sert et la verrouille.**

**2.2 Canonisation ≠ preuve d'unicité — collisions bloquées (garde anti-jointure-fausse).** §2 : le
producteur **ne déduplique pas** ; toute collision de `{zone_ref_canon_v1, reglement_number}` entre valeurs
verbatim est publiée dans `canonical_collisions`, comptée `blocked_canonical_collision` et **retirée de
`joinable`**. Le consommateur garde toujours `zone_ref_verbatim`. **→ garde structurelle contre une jointure
ambiguë : point d'appui direct pour le dissent #7 (§3).**

**2.3 Les 6 types de D03 → objets servis geo (mapping + réserves).**
| Type D03 | Objet servi geo | Réserve |
|---|---|---|
| règlement | `reglement_numero` + `reglement_millesime` (millésime métier ≠ `generated_at`) + provenance via `zone_source_url` | l'**association servie** numéro/URL/millésime « sans inférence municipale » = livrable **G01** (`fix/regulation-served-association`), pas encore un objet règlement autonome |
| source PDF | `zone_source_url` (provenance) + **index PV** (§5, `index_only`, **octets non servis**) | geo sert l'**index** PV, pas les octets (§6) |
| grille-norme | colonnes normes / **artefact 4a** delta-grille (clé identique, 3ᵉ composante = `densite_apres_reglement`, jamais repli sur `reglement_numero`) | 4a `complete:true` ≠ couverture 1 106 (§4) |
| document preuve | `proof` = `structurally_valid`/`absent`/`invalid` | **structurel ≠ preuve v2** (§2.5) |
| couche **environnementale** | **absent du contrat servi v1** | = **D07** (§4) — surface de service à créer |
| couche **utilisateur** | **non canonique geo** ; geo §6 ne porte « aucun id/projection de nœud d'un consommateur » | = fork **dissent #3** (§5), service futur **G03** |

**2.4 États d'absence honnêtes + partitions fermées.** D03 exige « états d'absence honnêtes ». geo §3 :
`known + explicit_unknown + absent + invalid = feature_count` ; partition-ville **ferme sur 1 106** ;
`explicit_unknown` **jamais** `known` ni `complete`. Une erreur réseau/lecture n'est **jamais** convertie en
absence (§1). **→ conforme, et plus strict que « honnête » : c'est mesuré et fermé.**

**2.5 Garde d'homonyme (piège produit majeur).** §3/§4 : `usage_dominant` servi = usage de la **zone Geo**,
**jamais** le champ homonyme d'un **Signal Immo** ; 4a expose `geo_zone_usage_dominant`, séparé « par nom et
objet ». **→ D06 doit interdire à D03 de confondre les deux `usage_dominant` ; geo le garde déjà côté producteur.**

**2.6 `proof` structurel vs preuve v2 (frontière à graver dans D06).** §3 : `structurally_valid` = passe le
garde de forme (`url/retrieved_at/sha256`, niveau, cohérence) ; ce **n'est pas** une preuve v2 revalidée (qui
exige le triplet de capture exact + clé CAS + rehash, cf. `zonage-proof.ts` + `capture/manifest.ts`). **→ le
consommateur ne doit pas traiter un `structurally_valid` servi comme une preuve v2.**

**2.7 Contrat MCP.** D03 demande un contrat MCP. Le contrat servi geo est un **manifeste S3 versionné +
haché** (`latest.json` compare-and-swap → snapshot immuable nommé par sha256, §1). La **surface MCP** (comment
immo interroge geo) relève du consommateur (PLAN §7 : « Radar : consommation Geo, MCP métier »). **→ pas un
gap geo ; à cadrer côté Radar par-dessus le contrat S3 versionné.**

## 3. D06 — dissent **#7** PRÉSERVÉ

> #7 : contrat règlement *représentatif par signal* vs relation *explicite signal→zone→règlement avec preuve propre*.

Le contrat servi geo atterrit **sans ambiguïté sur le côté explicite** : il sert `reglement_numero` **par
zone** sous la clé canonique, **bloque** les jointures en collision (§2.2), et **ne sert aucun niveau
municipal comme preuve** d'une relation (§6 ; cf. PLAN §4 « aucun niveau municipal utilisé comme preuve d'une
relation signal-règlement »). **Je ne lisse pas le dissent** : un *représentatif par signal* peut rester
désirable côté UX immo, mais **geo ne le SERVIRA pas comme preuve** — la tension « commodité UX vs preuve
explicite » reste visible et **owner-gated**. L'implémentation de l'association explicite servie = **G01**
(dépend de D06). Tant que la triade est absente/inconnue/invalide/en-collision, **geo ne sert pas de
jointure** (§6) — immo doit rendre cet état, pas inventer un règlement.

## 4. D07 — validation détaillée (audit sources environnementales)

**4.1 Surface de service manquante (le constat central).** Les couches environnementales (BDZI = zones
inondables, GRHQ = réseau hydrographique, CPTAQ = zones agricoles protégées) **ne figurent PAS** dans
`SPEC_GEO_SERVED_CONTRACT` v1 (qui couvre zonage/règlement/usage/PV). **→ D07 est un livrable neuf réel** :
un audit **+** (à terme) une **surface de service dédiée**, pas une simple validation d'existant.

**4.2 Axes d'audit (cadre correct).** L'item nomme les bons axes par source : **autorité, licence,
fréquence, CRS, couverture, limites**. geo est bien le propriétaire de ces axes (PLAN §7 : « Geo :
acquisition, licence, CRS, provenance, qualité, données canoniques »). L'audit doit livrer, **par source**
(BDZI/GRHQ/CPTAQ) : source autoritaire, droits de redistribution, cadence de mise à jour, projection/CRS,
emprise spatiale, et **limites/lacunes connues** (états d'absence).

**4.3 Disciplines de service à hériter de v1 (pour ne pas régresser).** Toute surface servie
environnementale doit reprendre : manifeste **versionné + haché** compare-and-swap (§1), **partitions
fermées** + `explicit_unknown ≠ known` (§3), **provenance par source** (analogue `zone_source_url/level`),
**acquisition cluster→S3 uniquement, aucune capture locale** (G02 ; principe fondateur geo). L'artefact
Warden reproductible (G02) est la preuve de bout en bout.

## 5. D07 — dissent **#3** PRÉSERVÉ

> #3 : stockage des couches utilisateur *dans Geo* vs *métadonnées/ACL dans Radar + blobs géographiques dans Geo*.

Distinction à tenir ferme : les couches **environnementales** = **canoniques, geo-owned** (autorité/licence/CRS
= geo) → **pas** de fork. Les couches **utilisateur** = **fork non tranché**. Indice de cadrage : geo §6 ne
porte « aucun id/projection de nœud d'un consommateur » — ce qui est **cohérent avec la position médiane de
#3** (ACL/métadonnées côté Radar, blobs géographiques côté Geo), mais **ne la ratifie pas**. **Je ne lisse
pas** : le choix « tout dans Geo » vs « ACL Radar + blobs Geo » reste ouvert, porté par **G03**
(`feat/city-user-layer-service`), **owner-gated**. Garde geo à préserver dans les deux cas : **aucun passage
automatique d'une couche utilisateur au canon geo** (PLAN P5 G03 ; principe de promotion explicite).

## 6. « geo = propriétaire du module carto » (DOSSIER §9) — cohérence avec D06/D07

Le renversement §8 (DS-owned, validé par geo) → §9 (**GEO-OWNED, DS-compliant**) est **cohérent** avec
D06/D07 : geo possède déjà **le contrat de données servi** (SPEC_GEO_SERVED_CONTRACT) ET, côté runtime, le
**moteur carto renderer-neutre** (mon `SPEC_GEO_MAP_ENGINE`, ADR-0025). D06 (contrat data) et D07 (sources
environnementales) sont la **face données** de cette propriété ; le moteur en est la **face runtime**. Aucun
conflit : la propriété geo est data **et** runtime, le DS porte le chrome, immo l'adaptateur métier mince.
